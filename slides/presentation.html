CourseAI / Slide 2

The product is more than chat: it is an evented curriculum workspace with evaluation built in.

Architecture flow

Step 1
Convex as canonical state
Programs, courses, enrollment, faculty, policies, reviews, action items, messages, and audit logs live in one backend.
Step 2
Scoped evidence retrieval
The agent loads a bounded course and policy packet instead of writing from a vague context blob.
Step 3
Gemini tool calling
10 internal tools handle curriculum facts first. Google Search grounding is only used when fresh external context materially helps.
Step 4
Durable streaming
The UI subscribes to messageEvents, so users see plan creation, execution progress, streamed text, sources, and quality checks in the assistant rail.

CourseAI / Slide 3

The key design tradeoffs were about curriculum workflow fit, not chasing the flashiest stack.

Stack decisions

Decision Why it won Tradeoff
Convex-first backend Realtime courses, enrollment, faculty, messages, streaming state, and audit logs all live together. Dedicated vector systems can be stronger on retrieval depth, but retrieval is not the whole product here.
Harnessed agent, not one-shot chat Bounded evidence + tool calls + trace + quality checks gives much better academic trust. More engineering work than a single LLM call.
Pro-class model selectively Broader department synthesis and complex prerequisite analyses benefit from stronger reasoning. Routine cases can often move to cheaper planner or deterministic paths later.
Durable streaming over plain SSE Replay, auditability, and faculty-visible progress mattered more than the fastest possible demo setup. More backend and UI complexity.
Deterministic fallback for single-course queries When a course + policy match is high-confidence, render directly from structured data without LLM latency. Less flexible for ambiguous queries, but faster and more reliable for common cases.
